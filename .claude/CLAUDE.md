## 硬约束

1. **文件写入策略**：

   **写入前必须先列计划（强制）**：在动手写任何笔记或综述之前，必须先在对话中输出：
   ```
   📋 写入计划：预估总字数 X 字，分 Y 段
   第1段（PART1）：frontmatter + 引言，约 Z 字
   第2段（PART2）：核心章节A，约 Z 字
   ...
   ```

   **分段写入规则**：每段严格不超过 **5,000 字**，超出 `Write` 工具会报 `content is missing`。

   **Write + Edit 分段策略**（不得使用 python3 或 Bash heredoc）：
   - 第一段：`Write` 工具创建文件，内容末尾加锚点 `<!-- CONTINUE -->`
   - 后续段：`Edit` 工具将上段末尾的 `<!-- CONTINUE -->` 替换为「新内容 + `<!-- CONTINUE -->`」
   - 最后段：`Edit` 工具将最后的 `<!-- CONTINUE -->` 替换为结尾内容（不再加锚点）

   **禁止**：`Bash` + `cat << 'EOF'`、`Bash` + 参数拼接内容、单次 Write 超过 5,000 字
2. **进度汇报**：执行耗时任务时，每完成一个步骤或每隔 1-2 分钟必须向用户输出进度（做了什么、下一步是什么、是否遇到问题），不要长时间沉默
3. **工具调用失败处理**：重试 3 次仍失败必须立刻向用户报告，不要自己反复尝试浪费时间

## 📝 核心任务说明

> 当前共有三类任务，以下为**任务一**（论文/博客精读笔记生成）的完整流程：

### 第一步：解析原文
- 使用 `WebFetch` 抓取并解读目标论文/博客
- 提取：标题、作者、机构、年份、arXiv/DOI 链接、核心贡献、方法设计、实验结果

### 第二步：大范围检索相关工作（目标 20-30 篇，最少 10 篇）
- 检索来源一：用 `WebFetch` 抓取论文原文的**参考文献列表**，从中筛选相关论文
- 检索来源二：根据论文**关键词**，多轮使用 `WebSearch` 在 arXiv 和 Google Scholar 上检索
- 检索策略：
  1. 用论文标题搜索：`"<Title>" arxiv`
  2. 用核心关键词搜索：`site:arxiv.org <keyword1> <keyword2> LLM`
  3. 搜索先驱工作：`<topic> survey site:arxiv.org`
  4. 搜索近期 Follow-up：`<topic> 2024 2025 site:arxiv.org`
  5. 搜索对比基线：`<topic> benchmark SOSP OSDI ASPLOS 2024 2025`
- 重点覆盖：先驱/奠基工作、直接对比方法、近期 Follow-up、相关 Survey
- **数量要求**：目标收集 20-30 篇，硬下限 10 篇；所有引用论文必须来自实际检索结果，禁止编造

### 第三步：生成正式阅读笔记
- **输出路径**: `content/专业学习/<文章名称>.md`
- **格式**: 严格参照 `template/template.md` 的七节结构（见下方）
- **链接规范**: 在元数据行使用 `[[<Name>_paper|📄论文]]` 链接到参考文献文件
- **相关工作**：将检索到的论文整合到"动机与痛点"小节或单独的"相关工作"小节，按类别（先驱/对比/Follow-up）组织

### 第四步：生成参考文献笔记（仅记录用户给的论文）
- **输出路径**: `content/参考文献/paper/<Name>_paper.md`（学术论文）或 `content/参考文献/blog/<Name>_blog.md`（博客）
- **格式**: 参照 `AttnRes_paper.md` 的格式（见下方）
- **作用**: 作为 Wiki 节点，允许正式笔记通过 `[[<Name>_paper|📄论文]]` 引用
- ⚠️ **仅为用户提供的目标论文创建参考文献笔记**，检索到的相关论文不需要单独创建参考文献文件

### 第五步：追加日志
- **日志路径**: `.claude/logs/task_log.md`
- 每次任务完成后，追加一条记录（格式见下方）

## 📝 任务二：专题综述报告生成

> 用户不提供具体论文链接，而是给一个**专题文件**（如 `todo/survey.md`），由我完成文献检索与综述写作。

### 输入格式（专题文件的固定结构，参见 `todo/survey.md`）

```markdown
# 任务目标
请你检索…，为我写一篇关于…的调研综述报告

# 专题与关键词
"关键词1" "关键词2" ...

# 参考论文
（可以是具体论文列表，也可以写"无"）

# 需要回答的问题
1. 问题一
2. 问题二
...

# 我的思考
用户自己写的分析、理解、已有结论…
```

- **关键词**：必有，用于驱动检索
- **参考论文**：可能有，也可能写"无"
- **需要回答的问题**：可能有多达 10+ 个细化问题，综述必须全部覆盖
- **我的思考**：用户已有的理解与观点，必须融入综述正文

### 第一步：检索相关文献（目标 20-30 篇，硬下限 10 篇）
- 若用户提供了参考论文，先用 `WebFetch` 抓取其参考文献列表作为种子
- 基于专题关键词多轮 `WebSearch`，覆盖以下维度：
  1. 综述/Survey 类论文：`<topic> survey arxiv`
  2. 核心技术论文：`site:arxiv.org <keyword1> <keyword2>`
  3. 工程实践/系统论文：`<topic> system implementation 2024 2025`
  4. 针对用户每个具体问题单独检索相关论文
- 所有引用论文必须来自实际检索结果，禁止编造

### 第二步：写综述报告
- **输出路径**: `content/专业学习/<专题名称>.md`（专题名称取自任务目标或关键词，使用中文）
- **frontmatter**：包含 `title` 和 `tags`，tags 取关键词
- **格式要求**：
  - **不**遵循任务一的七节模板，章节结构由综述内容逻辑决定
  - 整体结构建议：引言 → 背景/基础概念 → 各子专题深入分析 → 问题逐一回答 → 总结与展望
  - **必须为用户"需要回答的问题"中的每一个问题单独设置一节或明确标注**，确保全部覆盖，不得遗漏
  - **必须将"我的思考"部分的内容融入正文**（可润色表达，但核心观点和结论不可丢弃或替换）
  - 引用论文时在文中标注来源，格式：`作者等人 [论文简称/关键词] 指出…` 或脚注形式
  - 可用对比表格、分类列表、流程图（Mermaid）等丰富呈现形式
  - 深度优先：对问题的回答应有实质内容（原理、公式、代码示例、工程细节），不做表面罗列
  - 若某个问题涉及具体工程实现（如算子代码、框架细节），应给出可查证的具体示例，不泛泛而谈

### 第三步：追加日志
- **日志路径**: `.claude/logs/task_log.md`
- 格式：
  ```
  ## [YYYY-MM-DD HH:MM] <专题名称> 综述
  - **专题文件**: todo/<文件名>.md
  - **正式笔记**: content/专业学习/<文件名>.md
  - **参考文献**: N/A（综述任务）
  - **关键词**: #tag1 #tag2
  - **摘要**: 一句话说明综述覆盖范围与主要回答的问题
  ```

## 📝 任务三：批量任务执行（Todo 目录批处理）

> 用户将多个任务文件放在 `todo/` 目录下，我需要逐一读取并执行，每次最多处理 50 个任务文件，或直到 todo 目录清空为止。

### 触发条件
- 用户说"执行 todo 目录下的任务"或"批量处理 todo 里的文件"等类似指令

### Todo 文件格式规范（以 `todo/survey.md`、`todo/量化.md` 等为参考示例）

每个 todo 文件均遵循以下五段式结构：

```markdown
# 任务目标
这是一个**任务一/任务二**类型的任务：...（必须在此标注任务类型）

# 专题与关键词
（任务一可写"无"；任务二必填关键词）

# 参考论文
（任务一填具体 URL；任务二可写"无"；可以是多个 URL）

# 需要回答的问题
（任务一通常写"无"；任务二填若干具体问题）

# 我的思考
（用户的分析与已有观点，必须融入最终输出）
```

- **任务类型判断**：读取"任务目标"字段中的 `**任务一**` 或 `**任务二**` 标注来判断执行哪种流程
- `#我的思考` 字段在两种任务中都必须融入最终笔记，不可忽略

### 执行流程

#### 第一步：扫描 todo 目录
- 列出 `todo/` 目录下所有 `.md` 文件（跳过非 md 文件）
- 若文件超过 50 个，**只处理前 50 个**，并在日志中注明剩余未处理数量；若不足 50 个则全部处理直到目录清空
- 按文件名字母序依次处理

#### 第二步：分批并行执行任务（sub-agent 上下文隔离）

**每个 todo 文件都必须通过 `Agent` 工具启动独立的 general-purpose sub-agent 来执行**，不在当前对话上下文中直接处理。这是避免多篇论文的内容互相污染的核心机制。

**并发数限制**：每批最多同时启动 **5 个** background sub-agent（`run_in_background: true`），等待本批全部完成后，再启动下一批。流程：
1. 读取全部待处理文件列表（最多 50 个），判断各自任务类型
2. 取前 5 个，同时启动 5 个 background sub-agent
3. 等待本批全部完成，逐个将 todo 文件移入 done/，向用户汇报进度
4. 取下一批 5 个，重复直到全部处理完毕

**在启动每个 sub-agent 之前，先读取对应 todo 文件，判断任务类型**，然后按类型选择不同的 prompt：

**任务一的 sub-agent prompt**：
```
你是一个论文笔记生成助手，工作在项目 /mnt/yinhao/note/myblog/。

请按顺序读取以下两个文件，完整了解所有规范和约束后再开始执行：
1. /mnt/yinhao/note/myblog/.claude/tasks/common_constraints.md  ← 硬约束与 Red Lines
2. /mnt/yinhao/note/myblog/.claude/tasks/task1_spec.md          ← 任务一完整流程

然后读取任务文件，执行任务：
/mnt/yinhao/note/myblog/todo/<文件名>.md

执行完成后：
1. 在日志中额外注明：来源文件 todo/<文件名>.md（任务三批处理）
2. 汇报生成了哪个笔记文件，路径是什么
```

**任务二的 sub-agent prompt**：
```
你是一个专题综述写作助手，工作在项目 /mnt/yinhao/note/myblog/。

请按顺序读取以下两个文件，完整了解所有规范和约束后再开始执行：
1. /mnt/yinhao/note/myblog/.claude/tasks/common_constraints.md  ← 硬约束与 Red Lines
2. /mnt/yinhao/note/myblog/.claude/tasks/task2_spec.md          ← 任务二完整流程

然后读取任务文件，执行任务：
/mnt/yinhao/note/myblog/todo/<文件名>.md

执行完成后：
1. 在日志中额外注明：来源文件 todo/<文件名>.md（任务三批处理）
2. 汇报生成了哪个笔记文件，路径是什么
```

> **关键**：任务一的 sub-agent 只看 `task1_spec.md`，任务二的 sub-agent 只看 `task2_spec.md`，两者互不干扰，也不会加载整个 CLAUDE.md。

Sub-agent 返回后：
1. **重命名并移入 done 目录**：将 todo 文件以**笔记标题**重命名后移入 done/。命名规则：取生成的阅读笔记文件名（不含路径和后缀），例如笔记生成为 `content/专业学习/大模型量化调研.md`，则：
   ```bash
   mv /mnt/yinhao/note/myblog/todo/<原文件名>.md /mnt/yinhao/note/myblog/done/大模型量化调研.md
   ```
   - 文件名取笔记的中文标题（与 `content/专业学习/` 下生成的 `.md` 文件同名）
   - 若 sub-agent 未返回笔记文件名（任务失败等情况），则以 `<原文件名>_<YYYYMMDD>.md` 格式重命名后移入 done/，例如 `task1_20260409.md`，避免与后续同名文件冲突
2. **立即向用户汇报进度**：`✅ 已完成第 X/Y 个：<原文件名> → <生成的笔记路径>`
3. 继续处理下一个文件

#### 第三步：追加批量汇总日志

所有子任务完成后，在 `.claude/logs/task_log.md` 末尾追加汇总记录：

```
## [YYYY-MM-DD HH:MM] 任务三批处理汇总
- **处理文件数**: X 个
- **生成笔记列表**:
  - content/专业学习/<笔记1>.md（来自 todo/<文件1>.md）
  - content/专业学习/<笔记2>.md（来自 todo/<文件2>.md）
  - ...
- **移入 done 目录**: done/<文件1>.md, done/<文件2>.md, ...
- **跳过/失败**: （如有，列出原因）
```

### 注意事项
- **上下文隔离**：每个子任务必须通过独立 sub-agent 执行，不在主对话中直接展开，这是防止多篇论文内容互相污染的唯一方式
- **并发限制**：每批最多同时运行 5 个 sub-agent（`run_in_background: true`），一批完成后再启动下一批，禁止一次性启动超过 5 个
- **done 目录**：子任务成功完成后立即将 todo 文件移入 `/mnt/yinhao/note/myblog/done/`，失败则不移动，避免重复或遗漏
- 每完成一批后必须**立即向用户汇报进度**，不得连续沉默
- 若某个 todo 文件格式异常（缺少"任务目标"字段或无法判断任务类型），跳过并记录原因，继续下一个
- Sub-agent 失败（重试 3 次仍失败）：不移动 todo 文件，在汇总日志记录失败，继续处理下一个
- 本次批处理不处理 `done/` 目录中已完成的文件，也不处理 `todo/` 目录外的文件

## 📝 任务四：知识图谱关系整理

> 扫描 `content/专业学习/` 中所有已完成的笔记，分析它们之间的知识关联，然后回写每篇笔记的知识图谱索引字段。

### 触发条件
- 用户说"整理笔记关系"、"更新知识图谱"、"跑任务四"等类似指令

### 执行流程

#### 第一步：全量扫描所有笔记

用 Bash 列出 `content/专业学习/` 下所有 `.md` 文件：
```bash
ls /mnt/yinhao/note/myblog/content/专业学习/*.md
```

对每篇笔记，用 `Read` 读取并提取以下字段（无需读全文，重点读前 60 行）：
- `title`（frontmatter）
- `tags`（frontmatter）
- `## 🧠 核心摘要 (TL;DR)` 的内容
- `## 🕸️ 知识图谱索引` 的关键词行

将所有笔记汇总为一张**内部索引表**：

| 文件名（无后缀） | 标题 | 关键词/tags | 一句话摘要 |
|-----------------|------|-------------|-----------|
| AttentionRes | ... | ... | ... |
| KV稀疏调研 | ... | ... | ... |
| ... | | | |

#### 第二步：推理三类关系

基于索引表，逐篇分析每篇笔记与其他笔记的关系，填写三类字段：

**关系定义**：

| 字段 | 含义 | 判断标准 |
|------|------|---------|
| **前置知识 (Prerequisites)** | 读懂本文需要先了解的概念/方法，本文建立在其之上 | B 是 A 的基础理论、先驱方法、或 A 直接引用并依赖了 B 的核心概念 |
| **相关节点 (Related Notes)** | 同一领域/问题的平行研究，可互相参照 | A 和 B 都在解决同一类问题，但方法不同；或研究对象高度重叠 |
| **向下延申 (Successors)** | 本文催生的后续方向，或应用本文方法的扩展研究 | B 是在 A 的基础上进一步发展的；或 A 的方法被 B 应用到新场景 |

**关系约束**：
- 关系必须是**双向一致的**：若 A 的 Prerequisites 包含 B，则 B 的 Successors 应包含 A
- 若 A 的 Related Notes 包含 B，则 B 的 Related Notes 也应包含 A
- 不强求每篇都填满三个字段，无明确关系时留空（删除注释行即可）

**典型关系示例**（基于现有笔记）：
- `KV稀疏调研` 是 `KvZap`、`RL中的KV稀疏讨论` 的前置知识（综述先于具体方法）
- `KvZap` 与 `RL中的KV稀疏讨论` 是相关节点（同属 KV 稀疏方向）
- `ShiftParallelism` 与 `ZipServ`、`MSched` 相关（都是 LLM 推理系统优化）
- `AttentionRes` 与 `KV稀疏调研` 相关（都涉及注意力机制优化）

#### 第三步：逐篇回写笔记

对每篇笔记，找到 `## 🕸️ 知识图谱索引` 段落，将注释掉的三行替换为真实内容。

**目标格式**（替换掉注释）：
```markdown
## 🕸️ 知识图谱索引
- **关键词 (Keywords)**: #tag1 #tag2
```

## 🖼️ 图片插入规范（Quartz v4 + GitHub Pages）

> 站点部署在 `https://ramessesyin.github.io/myblog/`，baseUrl = `RamessesYin.github.io/myblog`，图片路径需带 `/myblog` 前缀。

### 图片存放位置
- 统一放在 `content/assets/<主题名>/` 目录下，例如 `content/assets/AFD/`
- **不要**放在 md 文件同级目录（目录太乱），**不要**放在 md 文件的子目录 `images/`（Quartz 会把相对路径转成 `../../images/xxx`，导致跨层级路径错误）

### 文档中引用方式
```markdown
![图片说明](/assets/AFD/image1.png)
```
- 必须用以 `/assets/` 开头的路径
- 不要用相对路径（如 `images/image1.png` 或 `./image1.png`），Quartz 会将其错误地转换为相对 URL

### 原理说明
- Quartz 处理相对路径时会基于页面 URL 拼接，导致子目录页面的图片路径跳级错误
- 使用路径 `/assets/xxx` 可绕过此问题，直接命中 GitHub Pages 静态资源
