# Towards Fully-fledged GPU Multitasking via Proactive Memory Scheduling

> [!abstract] 论文元数据
> **作者**: Weihang Shen, Yinqiu Chen, Rong Chen, Haibo Chen
> **年份**: 2025
> **关联论文**: [[]]

## MSched：基于主动内存调度的 GPU 多任务处理机制深度解读报告

## 1\. 执行摘要 (Executive Summary)

随着人工智能技术的迅猛发展，特别是大语言模型（LLM）和深度神经网络（DNN）在各行各业的广泛应用，GPU 计算平台已成为现代数据中心和边缘设备的核心算力基座。然而，GPU 算力（FLOPS）的增长速度远超显存容量（HBM Capacity）的增长，导致“内存墙”（Memory Wall）问题日益严峻。在多租户云环境或高并发推理场景下，多个显存密集型任务同时运行不可避免地导致显存超额订阅（Oversubscription）。

本报告深入解读了上海交通大学并行与分布式系统研究所（IPADS）发布的最新研究成果——**MSched (GPU Multitasking via Proactive Memory Scheduling)** 。该研究针对现有操作系统在处理 GPU 显存超额订阅时的根本性缺陷——即依赖被动、高延迟的按需分页（Demand Paging）机制——提出了一种革命性的**主动内存调度**架构。  

研究指出，传统的按需分页机制（如 NVIDIA Unified Memory）在面对 GPU 任务时会产生高达 **78 倍** 的性能衰减 。这是由于 GPU 的大规模并行架构导致单一页错误（Page Fault）会阻塞整个计算单元（CU）上数千个线程，以及 GPU 访存模式极差的局部性（Locality）导致的频繁页面颠簸（Thrashing）。  

MSched 的核心创新在于利用 GPU 内核（Kernel）访存模式的高度可预测性，通过**模板化预测（Template-based Prediction）** 和 **任务调度器与内存管理器的协同设计（Co-design）**，将显存管理从“被动响应”转变为“主动规划”。系统在任务执行前即可精确计算出所需的工作集（Working Set），并在上下文切换期间利用流水线技术完成数据迁移，从而实现了计算与数据传输的重叠。

评估结果显示，在显存严重超额订阅的情况下，MSched 相比传统按需分页机制，在科学计算和深度学习负载上实现了 **11.05 倍** 的性能提升，在 LLM 推理负载上更是实现了惊人的 **57.88 倍** 的吞吐量增长 。本报告将从技术背景、系统架构、核心算法、实验评估及行业影响等多个维度，对 MSched 进行详尽的拆解与分析。

## 2\. 研究背景与问题陈述 (Background & Problem Statement)

### 2.1 GPU 算力与存储的鸿沟

在过去的十年中，GPU 的架构演进主要集中在提升并行计算能力上。以 NVIDIA 的架构演进为例，从 Pascal 到 Blackwell，张量核心（Tensor Core）的引入使得 FP16/BF16 算力呈指数级增长。然而，显存容量的增长却受到物理封装和成本的严格限制。例如，即使是旗舰级的 RTX 5080，其 HBM 容量（16GB）在面对参数量高达 70B 甚至更大的现代 LLM 模型时也显得捉襟见肘 。  

这种算力与存储的不匹配导致了严重的资源浪费：

1.  **单任务独占导致的低利用率**：为了避免显存溢出（OOM），目前的调度策略往往采用独占模式，即一个 GPU 在同一时间只运行一个大模型任务。这导致在推理间歇期或计算非密集阶段，昂贵的计算单元处于闲置状态。
    
2.  **多任务并发导致的显存争抢**：为了提高利用率，云服务商希望在同一 GPU 上通过时分复用（Time-Slicing）或空分复用（MIG/MPS）运行多个任务。然而，当这些任务的总显存需求超过物理显存上限时，操作系统必须介入进行显存交换（Swapping）。
    

### 2.2 传统操作系统的局限性：按需分页的崩溃

在 CPU 世界中，虚拟内存（Virtual Memory）技术通过按需分页（Demand Paging）完美解决了内存不足的问题。当程序访问不在物理内存中的页面时，CPU 触发缺页异常（Page Fault），操作系统挂起该线程，从磁盘加载数据，更新页表，然后恢复执行。这种机制对应用程序是透明的。

NVIDIA 通过统一内存（Unified Memory, UM）技术将这一机制引入了 GPU。然而，MSched 的作者敏锐地指出，这种直接移植的机制在 GPU 架构上表现出了严重的“病理特征”（Pathology）：  

#### 2.2.1 大规模并行带来的惩罚放大

GPU 采用 SIMT（单指令多线程）执行模型。一个 warp（32 个线程）甚至一个线程块（Block）中的所有线程往往执行相同的指令。

-   **现象**：当一个线程触发页错误时，硬件内存管理单元（MMU）通常会锁定整个计算单元（CU）甚至流多处理器（SM）的 TLB（转译后备缓冲器）。
    
-   **后果**：这不仅阻塞了触发错误的那个线程，还导致该 CU 上数千个并发线程（即便是那些不需要访问该缺页数据的线程）全部停滞。
    
-   **数据支撑**：在 LLM 推理场景下，这种阻塞导致硬件利用率接近于零，性能下降 **78 倍** 。  
    

#### 2.2.2 极差的时间局部性与页面颠簸

CPU 程序通常具有良好的局部性（Locality），即最近访问的数据很可能在不久后再次访问。然而，GPU 负载（尤其是 LLM 和科学计算）通常是流式（Streaming）的。

-   **场景**：在矩阵乘法或注意力机制（Attention）计算中，内核会快速扫描数 GB 的数据。
    
-   **结果**：旧的 LRU（最近最少使用）替换算法失效。当页面被换入时，它可能只被使用一次就被后续的大量数据流冲刷出显存。当下一轮迭代需要该页面时，又必须重新从主机 DRAM 换入。这种现象被称为“页面颠簸”（Thrashing），导致 PCIe 总线被无效的数据搬运占满，而计算单元却在等待数据 。  
    

### 2.3 现有解决方案的不足

为了解决上述问题，学术界和工业界提出了多种方案，但均存在局限性 ：  

-   **计算调度器 (如 XSched, NVIDIA MPS)**：专注于计算资源（SM）的划分，假设显存容量充足。一旦显存不足，回退到原生驱动的按需分页，性能崩塌。
    
-   **单任务显存优化 (如 SwapAdvisor, Sentinel)**：针对单一深度学习训练任务进行显存交换优化。它们无法感知多任务环境下的竞争，导致跨任务的页面互相驱逐（Cross-task Thrashing）。
    
-   **模型层优化 (如 vLLM)**：通过优化 KV-Cache 的显存布局减少碎片，但这属于应用层优化，无法解决物理显存总容量不足时的系统级调度问题。

## 3\. MSched 系统架构与设计哲学 (Architecture & Design)

MSched 的设计基于一个核心洞察：**GPU 任务的访存模式是高度可预测的**。与 CPU 程序中充满随机跳转和指针引用的“黑盒”行为不同，GPU 内核（Kernel）通常是基于规则数据结构（张量、矩阵）的数学运算，其访问的内存地址范围几乎完全由**启动参数**（Launch Arguments）决定 。  

基于此，MSched 提出了**主动内存调度**（Proactive Memory Scheduling）的概念，将显存管理从“运行时响应”提前到“调度时规划”。

### 3.1 扩展的上下文切换 (Expanded Context Switch)

MSched 重新定义了 GPU 上下文切换的边界。

-   **传统定义**：保存/恢复寄存器状态、共享内存状态。显存内容保持不变（依赖后续的 Page Fault 换入）。
    
-   **MSched 定义**：除了保存寄存器，还包含**主动恢复工作集（Working Set）**。即在切换到下一个任务之前，系统通过 DMA 引擎主动将该任务即将用到的数据块从主机内存批量迁移到 GPU HBM 中，并预先更新页表。
    

这种设计将分散的、高昂的 4KB 粒度页错误处理，转化为高效的、大块的 PCIe 数据传输，从而掩盖了数据移动的延迟。

### 3.2 系统组件全景

MSched 主要由以下三个核心组件构成 ：  

1.  **用户态预测器 (Userspace Predictor)**：以动态链接库（DLL）形式注入到应用进程中，拦截 CUDA API 调用，实时预测内核的显存访问范围。
    
2.  **全局协调器 (Centralized Coordinator)**：一个系统级守护进程，维护全局的**任务调度时间线（Task Scheduling Timeline）**，负责决策“何时”以及“迁移哪些”页面。
    
3.  **内核态驱动扩展 (Kernel-mode Driver Extension)**：对 GPU 驱动的修改，增加了基于优先级的页面驱逐接口（madvise-like）和批量迁移引擎。

## 4\. 核心机制一：基于模板的显存预测 (Template-based Prediction)

为了实现主动调度，系统必须极其精确地知道下一个内核需要访问哪些内存页面。预测不足会导致页错误（性能损失），预测过度会导致显存污染（Eviction Thrashing）。

### 4.1 为什么不使用简单的分配粒度预测？

最简单的方案是：如果内核使用了数组 A，就将整个数组 A 迁移进显存。

-   **问题**：在深度学习和科学计算中，显存分配（Allocation）往往远大于单次内核访问的范围。例如，一个分块矩阵乘法可能只访问大矩阵中的一个子块（Tile）。
    
-   **数据**：MSched 的消融实验显示，基于分配粒度的朴素预测（Naive Prediction）在重度负载下会导致 **15.67 倍** 的性能下降，因为无用的数据挤占了宝贵的 HBM 空间 。  
    

### 4.2 三大访存模板 (Three Access Templates)

通过使用 NVBit 工具对大量 CUDA 内核进行离线分析，研究团队发现 99% 的内核访存模式可以归纳为三类数学模板 ：  

|模板类型|占比|描述|数学表达 (简式)|典型应用|
|---|---|---|---|---|
|**T1: 固定大小**|~77%|访问范围固定，不随参数变化或仅随不变参数变化。|归约操作 (Reduction)、全局计数器|
|**T2: 线性大小**|~18%|访问范围大小与启动参数的乘积成线性关系。|向量加法、全连接层、激活函数|
|**T3: 跨步访问**|~5%|访问多个不连续的块，块大小和跨度均为参数的线性函数。|张量切片 (Slicing)、多头注意力 (MHA)|

### 4.3 预测流程

1.  **离线学习阶段**：系统对目标内核进行 Profiling，记录不同输入参数下的访存地址。通过线性回归分析，确定该内核属于哪一类模板，并求解出公式中的系数（如 ）。这些公式被编码到数据库中。
    
2.  **在线推理阶段**：
    
    -   应用调用 `cudaLaunchKernel`。
        
    -   MSched 拦截调用，提取参数（Grid Dim, Block Dim, 指针, 标量参数）。
        
    -   代入离线生成的公式，计算出精确的内存页范围（Page Bitmap）。
        
    -   将预测元数据（Metadata）附加到指令流中发送给调度器。
        

这一过程的开销极低（微秒级），且实现了 **0.00% 的假阳性率（False Positive）** 和仅 **0.25% 的假阴性率** ，保证了只迁移真正需要的数据。

## 5\. 核心机制二：调度器与内存管理器的协同设计 (Co-design)

即使知道了每个任务需要什么数据，如何在全球范围内协调多个任务的显存使用仍是一个难题。MSched 引入了\*\*任务调度时间线（Task Scheduling Timeline）\*\*作为“罗塞塔石碑”（Rosetta Stone），连接计算与存储 。

### 5.2 实现 Belady 的最优置换算法 (OPT)

经典的 Belady 算法认为，最优的页面置换策略是**驱逐那些在未来最长时间内不会被访问的页面**。在通用 OS 中，这是不可实现的，因为无法预知未来。但在 MSched 中，由于有了 Timeline，未来是已知的。

**反向扫描算法（Reverse-Scan Algorithm）** ： 当需要腾出空间时，内存管理器执行以下操作：  

1.  锁定当前的 Timeline。
    
2.  从时间线的最末端（最远的未来）开始反向遍历到当前时刻。
    
3.  **标记优先级**：
    
    -   最远任务需要的页面标记为“冷”（Cold）。
        
    -   最近任务需要的页面标记为“热”（Hot）。
        
    -   即将在下一个时间片运行的任务页面标记为“极热”（Critical）。
        
4.  **构建驱逐列表（Eviction List）**：驱动程序根据标记，优先驱逐“冷”页面。这确保了留在 HBM 中的数据必然是近期最需要的数据。
    

### 5.3 解决“策略冲突” (Policy Conflict)

在传统系统中，CPU 的内存管理器（LRU 策略）和 GPU 的计算调度器（Round-Robin 或 优先级策略）是割裂的。

-   _冲突场景_：调度器计划运行任务 A，但内存管理器刚因为任务 A 暂时不活跃而将其页面驱逐。
    
-   _MSched 解法_：通过协同设计，内存管理器的决策完全服从于调度器的计划。内存管理器**只**为调度器即将调度的任务服务，消除了这种内耗。

## 6\. 实现细节与优化 (Implementation Details)

为了将理论转化为高性能系统，MSched 在实现层面进行了多项微架构优化。

### 6.1 流水线化迁移 (Pipelined Migration)

普通的显存交换是半双工的（Stop-and-Wait）：暂停 GPU -> 拷出旧页 -> 拷入新页 -> 恢复 GPU。这浪费了 PCIe 的双向带宽能力。

MSched 实现了全双工流水线 ：  

-   利用 PCIe 的全双工特性，同时进行 Device-to-Host (D2H) 的驱逐和 Host-to-Device (H2D) 的预取。
    
-   **计算与传输重叠**：在当前任务 还在计算其最后几毫秒时，系统利用空闲的 PCIe 带宽开始预取下一个任务 的数据。
    
-   _效果_：在 RTX 3080 上，这种流水线设计将有效交换带宽从 22.2 GB/s 提升至 **39.8 GB/s**（1.79倍）。  
    

### 6.2 驱动层改造

研究团队对 NVIDIA 的开源 GPU 内核模块进行了修改（尽管报告未明确指出是 OpenRM，但提到了修改 KMD）。增加了以下原语：

-   `sys_gpu_madvise`：允许用户态协调器直接操纵驱动内部的 LRU 链表位置。
    
-   `sys_gpu_migrate_batch`：支持一次系统调用提交数千个页面的迁移请求，减少用户态/内核态切换开销。

## 7\. 实验评估 (Evaluation)

### 7.1 实验环境

-   **硬件平台**：
    
    -   **高端**：NVIDIA RTX 5080 (16GB HBM) —— 代表未来高性能消费级显卡。
        
    -   **主流**：NVIDIA RTX 3080 (10GB HBM)。
        
    -   **主机**：配备 128GB DDR5 内存的 Intel Xeon 平台。
        
-   **负载组合 (Workloads)** ：  
    
    -   **Combination A (MultiSci)**: 科学计算基准 (Rodinia: CFD, Hotspot)。
        
    -   **Combination B (MultiDNN)**: 经典 CNN 推理 (ResNet152, VGG19)。
        
    -   **Combination C (HybridDL)**: 混合负载 (DNN + LLM)。
        
    -   **Combination D (MultiLLM)**: 多路并发 Llama-3-8B 推理（显存压力最大）。
        

### 7.2 核心性能数据

实验在不同程度的显存超额订阅（150%, 200%, 300%）下进行。

#### 表 1：MSched 与 原生按需分页 (UM) 的吞吐量对比 (归一化加速比)

|负载类型|显存超订率|原生 UM (Baseline)|MSched|**加速比 (Speedup)**|
|---|---|---|---|---|
|**Sci/DNN**|150% (Light)|1.0x (Baseline)|11.05x|**11.05×**|
|**Sci/DNN**|200% (Medium)|1.0x|9.35x|**9.35×**|
|**Sci/DNN**|300% (Heavy)|1.0x|7.52x|**7.52×**|
|**MultiLLM**|150% (Light)|1.0x|57.88x|**57.88×**|
|**MultiLLM**|200% (Medium)|1.0x|44.79x|**44.79×**|
|**MultiLLM**|300% (Heavy)|1.0x|33.60x|**33.60×**|

**数据解读**：

-   在 LLM 负载下 **57.88倍** 的提升极其震撼。这并非 MSched 创造了奇迹，而是因为它避免了 UM 的灾难性崩溃。在 UM 模式下，LLM 的每一步 Decoding 都会扫描整个 KV-Cache，导致缺页风暴（Page Fault Storm），GPU 几乎处于停滞状态。MSched 通过预取，保证了计算时数据已在 HBM 中，从而维持了接近独占模式的性能。
    

### 7.3 延迟与公平性 (Latency & Fairness)

除了吞吐量，MSched 在服务质量（QoS）上也表现优异。

-   **长尾延迟 (P99)**：相比于仅做计算调度的 XSched，MSched 将实时任务的 P99 延迟降低了 **4.06 倍**。这是因为实时任务的数据准备不再受限于随机的页错误延迟。
    
-   **尽力而为任务 (Best-Effort)**：在保证高优先级任务的同时，后台任务的吞吐量提升了 **2.43 倍**。这证明了 MSched 通过高效利用 PCIe 带宽，提升了系统的**总吞吐量**（System-wide Throughput），做到了“把蛋糕做大” 。  
    

### 7.4 消融实验：预测精度的重要性

实验对比了 MSched 的模板预测与朴素预测（基于分配粒度）。

-   在轻负载下，两者差异不大。
    
-   在重负载（300%）下，朴素预测的性能发生了崩塌（Collapse），仅为 MSched 的 1/15。
    
-   **结论**：在显存极度稀缺时，**精度即性能**。迁移任何不需要的字节都是对系统资源的致命浪费。

## 8\. 相关工作对比 (Related Work)

为了确立 MSched 的学术地位，报告将其与现有的几类系统进行了对比 。  

|系统名称|目标场景|核心机制|局限性|
|---|---|---|---|
|**Unified Memory (UM)**|通用单任务|硬件 Page Fault|延迟高，并行度惩罚大，无法感知未来。|
|**SwapAdvisor / Sentinel**|单任务 DNN 训练|静态图分析 + 预取|仅针对单一任务，多任务并发时会互相驱逐数据。|
|**NVIDIA MPS**|多任务计算|空间/时间分片|假设显存充足，不处理 Over-subscription。|
|**vLLM / PagedAttention**|LLM 推理|逻辑显存分页|解决碎片问题，但不解决物理显存不足时的换入换出。|
|**MSched (本文)**|**多任务并发 + 超额订阅**|**OS级主动调度 + 模板预测**|**首个解决多任务显存争抢的系统级方案。**|

**深度见解**：MSched 实际上填补了“计算调度器”（如 MPS）和“显存分配器”（如 vLLM）之间的空白。它是一个**物理显存调度器**，负责在多个应用之间仲裁物理 HBM 的使用权。

## 9\. 结论与未来展望 (Conclusion & Future Outlook)

### 9.1 研究总结

MSched 的提出标志着 GPU 操作系统设计的一个转折点。它证明了在异构计算时代，通用的、黑盒式的资源管理策略（如按需分页）已经失效。通过引入**领域知悉（Domain-Aware）** 的机制——即利用 GPU 程序的确定性特征——操作系统可以实现数量级的性能飞跃。

核心贡献总结：

1.  **定量分析**：揭示了按需分页在 GPU 上的病理特征（78x Slowdown）。
    
2.  **算法创新**：提出了基于模板的微秒级显存预测算法。
    
3.  **架构突破**：实现了基于时间线的全局最优（OPT）页面置换策略。
    
4.  **工程实践**：在真实硬件上验证了 LLM 推理场景下的 50+ 倍性能提升。
    

### 9.2 行业影响与启示

1.  **云成本的重新计算**：MSched 使得云服务商可以在不增加物理 GPU 的情况下，安全地超卖（Oversell）显存资源。这意味着在同一张 H100/RTX 5080 上可以部署更多的并发实例，大幅降低单位 token 的推理成本。
    
2.  **Serverless GPU 的新范式**：当前的 Serverless GPU 面临冷启动慢（加载模型）或由于 Keep-Alive 导致显存浪费的问题。MSched 支持“温启动”（Lukewarm），即模型驻留在主机内存，计算时毫秒级换入，这将极大地推动 Serverless AI 的普及。
    
3.  **硬件设计的演进**：MSched 的成功可能会影响下一代 GPU 架构（如 NVIDIA Rubin）。未来的 GPU 可能会在硬件层面集成类似的“预取引擎”或“命令队列分析器”，将 MSched 的软件逻辑固化到芯片中，以进一步降低延迟。
    

### 9.3 局限性

尽管表现出色，MSched 仍依赖于内核访存的**可预测性**。对于那些访存地址依赖于运行时数据内容（Data-dependent memory access）的不规则负载（如某些图计算算法），模板预测可能会失效。未来的工作需要探索如何结合动态分析或推测执行（Speculative Execution）来覆盖这些长尾场景。
