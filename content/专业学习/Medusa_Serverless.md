## 🧠 核心摘要 (TL;DR)
> 无服务器 LLM 推理面临三阶段冷启动问题（模型加载 + KV Cache 初始化 + CUDA 图构建），TTFT 尾延迟极高。Medusa 将 CUDA 图和 KV Cache 初始化数据**离线物化**存储，在线阶段直接加载恢复，消除重复构建开销。在生产工作负载上，模型加载延迟降低 42.5%，TTFT 尾延迟降低 53.0%。

## 🎯 动机与痛点

### 现有方案的瓶颈

无服务器计算（Serverless / FaaS）因其弹性伸缩、按需付费的特性，成为 LLM 推理服务部署的重要方向。然而，LLM 推理与传统无服务器函数相比，冷启动开销极为严重：

**三阶段冷启动问题：**
1. **模型加载（Model Loading）**：将数十 GB 的模型权重从存储（NVMe / 远程对象存储）加载到 GPU 显存，耗时数秒至数十秒
2. **KV Cache 初始化（KV Cache Init）**：为当前推理请求预分配并初始化 Key-Value Cache 内存池
3. **CUDA 图构建（CUDA Graph Capture）**：在 GPU 上捕获（capture）计算图，包括算子融合、内存地址绑定等步骤，对于大型模型可能需要数分钟

每次冷启动都要**重复执行所有三个阶段**，导致首 Token 时间（TTFT, Time-To-First-Token）在高延迟尾部（P99）极高，严重影响用户体验和 SLO 达成。

**CUDA 图非确定性难题：**
CUDA 图中记录的算子地址（内存指针、CUDA 核函数地址）在每次程序启动时会因 ASLR（地址空间随机化）和运行时内核注册顺序等原因发生变化，无法直接将 CUDA 图序列化保存后下次复用——这正是过去没有系统尝试物化 CUDA 图的根本原因。

**论文的切入点**：
Medusa 提出通过**离线物化（Offline Materialization）**技术，将 CUDA 图和 KV Cache 初始化信息在首次运行时完整记录下来，并开发配套的**在线恢复（Online Restoration）**机制解决地址非确定性问题，使后续实例的冷启动跳过构建阶段，直接载入物化快照。

## ⚙️ 核心设计与机制

### 整体架构：离线-在线两阶段协作

Medusa 的核心思想是将冷启动中所有可以**确定性预计算**的部分移到离线阶段完成，在线阶段仅执行**快速恢复**。系统分为两个主要阶段：

```
┌─────────────────────────────────────────────────────┐
│                   离线物化阶段                         │
│  模型首次部署时运行一次                                  │
│  ┌──────────────┐  ┌──────────────┐                 │
│  │ KV Cache     │  │ CUDA Graph   │                 │
│  │ 初始化物化    │  │ 物化与序列化  │                 │
│  └──────┬───────┘  └──────┬───────┘                 │
│         │                 │                          │
│         ▼                 ▼                          │
│       持久化存储（NVMe / 共享存储）                     │
└─────────────────────────────────────────────────────┘
                         │
                         │（后续每次实例启动）
                         ▼
┌─────────────────────────────────────────────────────┐
│                   在线恢复阶段                          │
│  ┌──────────────────────────────────────────────┐   │
│  │ 1. 模型权重加载（并行优化）                      │   │
│  │ 2. KV Cache 物化数据直接恢复（跳过初始化逻辑）    │   │
│  │ 3. CUDA Graph 物化数据恢复（解决地址非确定性）    │   │
│  └──────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘
```

### 关键技术点 1：KV Cache 初始化物化

**问题背景：**
LLM 推理框架（如 vLLM）使用 PagedAttention 将 KV Cache 组织为固定大小的"块（block）"，并在推理前通过一系列 CUDA 核函数完成内存块分配、初始化（清零/填充特定值）、建立块表（block table）映射等操作。这些操作虽然每次结果相同，但需要消耗一定的 GPU 计算和主机-GPU 通信时间。

**Medusa 的解法：**
在离线阶段，Medusa 完整记录 KV Cache 初始化完成后的 GPU 内存状态（包括块内容、块表结构、引用计数等元数据），将其序列化保存到持久存储。

在线阶段，直接将物化的 KV Cache 快照映射到 GPU 内存，**跳过所有初始化计算逻辑**，等效于从检查点热启动 KV Cache。

### 关键技术点 2：CUDA 图物化与地址非确定性问题

这是 Medusa 最核心的技术挑战。

**CUDA 图基础：**
CUDA 图（CUDA Graph）是 NVIDIA 提供的一种优化机制，将一系列 GPU 操作（内核调用、内存拷贝等）记录为有向无环图，通过一次 Launch 完成整图的执行，避免每次迭代的 CPU 调度开销，是现代 LLM 推理框架（vLLM、TensorRT-LLM 等）的标准加速手段。

**CUDA 图的非确定性来源：**
CUDA 图中的节点记录了具体的 GPU 内核函数地址（device function pointer）和内存地址（device pointer）。这些地址在每次进程启动时都会发生变化，原因包括：
- **ASLR（Address Space Layout Randomization）**：操作系统对进程内存布局随机化
- **CUDA 运行时动态加载**：内核函数在 CUDA context 初始化时动态注册，注册顺序和地址依赖运行时状态
- **内存分配器不确定性**：GPU 内存分配的起始地址每次可能不同

因此，CUDA 图不能直接序列化保存后在新进程中重用——保存的地址在新进程中已经失效。

**Medusa 的两项核心创新：**

**① 离线-在线协作的参数恢复（Offline-Online Cooperated Parameter Restoration）**

Medusa 将 CUDA 图中的地址信息分为两类：
- **不变部分（Topology + Op Types）**：图的拓扑结构、算子类型，离线序列化保存
- **可变部分（Addresses）**：内存地址和内核函数地址，在线阶段动态重新绑定

系统在离线阶段额外记录每个地址的**语义标签**（即该地址对应哪个张量、哪个内核函数，用相对标识符表示），在线恢复时，Medusa 在新进程中重新分配对应资源并完成地址重映射，再将更新后的地址写入物化的 CUDA 图节点。

数学上，设离线物化的 CUDA 图节点参数为 $P_{offline}$，在线绑定后的新地址集合为 $A_{online}$，则恢复过程为：

$$P_{online} = \text{Restore}(P_{offline},\ A_{online},\ \text{SemMap})$$

其中 $\text{SemMap}$ 是离线阶段记录的语义映射表（Semantic Mapping Table）。

**② 触发内核增强的内核地址恢复（Triggering-Kernel Enhanced Kernel Address Restoration）**

对于 CUDA 图中的设备端函数指针（device-side function pointers，某些内核调用其他内核时使用），常规的主机端地址重映射无法直接访问这些指针。Medusa 引入了专门设计的"触发内核（Triggering Kernel）"：

1. 在离线阶段，为每个需要地址更新的设备端指针位置注入一个轻量级触发内核节点
2. 在线恢复时，这些触发内核在 GPU 上执行，直接在设备内存中完成对应地址的原子更新
3. 触发内核完成后，CUDA 图中所有地址已全部更新，可以安全重放（replay）

**整体 CUDA 图恢复流程：**
```
离线阶段：
  1. 捕获 CUDA 图（标准 cudaGraphCapture）
  2. 遍历所有节点，记录地址 → 语义标签的映射（SemMap）
  3. 识别设备端函数指针，注入触发内核节点
  4. 序列化拓扑结构 + SemMap → 持久存储

在线阶段：
  1. 加载序列化数据
  2. 重建图拓扑，分配新内存，获取新内核地址
  3. 根据 SemMap 更新主机侧节点参数（内存地址、主机可见内核地址）
  4. Launch 触发内核，更新设备侧函数指针
  5. 图恢复完成，可直接 replay
```

Medusa 在 **139,364 个 CUDA 图节点**的模型上成功实现了完整的物化恢复，验证了该机制的可扩展性。

### 关键技术点 3：模型权重加载并行优化

在模型权重加载阶段，Medusa 结合现有技术（如 ServerlessLLM 的多层加载思路）进行了并行优化：将模型权重的存储 I/O、主机内存 DMA 传输、主机到 GPU 的 PCIe 传输进行流水线化，减少各阶段的串行等待时间。

模型加载与 KV Cache / CUDA 图恢复也可部分重叠执行（因为 KV Cache 恢复和 CUDA 图节点修复对模型权重的依赖相对独立），进一步压缩端到端的冷启动时间。

## 📊 实验与性能评价

### 实验设置

- **评测平台**：配备 GPU 的服务器节点，模拟无服务器部署环境
- **工作负载**：真实生产工作负载（Production Workloads），包含不同请求长度分布和并发度
- **评测模型**：多个规模的 LLM 模型（具体参数见原文表格）
- **对比基线（Baseline）**：传统无服务器 LLM 推理系统（每次冷启动均重建 CUDA 图和 KV Cache）

### 主要实验结果

| 指标 | Medusa vs. Baseline |
|------|---------------------|
| 模型加载延迟 | **降低 42.5%** |
| TTFT 尾延迟（生产工作负载） | **降低 53.0%** |
| CUDA 图节点恢复规模 | **139,364 个节点**（成功验证） |

**模型加载延迟（-42.5%）**：通过 KV Cache 物化跳过初始化计算、CUDA 图物化跳过重建阶段，结合权重加载并行化，总体减少了冷启动中非权重传输部分的大量开销。

**TTFT 尾延迟（-53.0%）**：在生产工作负载下，原始系统的 P99 TTFT 受冷启动拖累极高；Medusa 通过消除重复的 CUDA 图捕获和 KV Cache 初始化，使绝大多数实例在加载模型权重后即可立刻服务请求，从而大幅压缩尾延迟。

### 局限性（Limitations）

1. **离线物化存储开销**：物化的 CUDA 图和 KV Cache 快照需要额外的持久化存储空间，对于超大规模模型（如 70B+），这一开销可能显著增加存储成本
2. **框架适配性**：目前的 CUDA 图物化机制与推理框架（vLLM 等）的具体实现深度耦合，跨框架迁移需要重新适配
3. **模型更新与版本管理**：当模型权重更新（Fine-tuning / 版本迭代）时，对应的物化快照必须失效并重新生成，增加了运维复杂度
4. **动态形状支持**：CUDA 图一旦捕获，其输入形状（batch size、序列长度等）固定，对动态序列长度场景需要维护多个不同形状的物化图，进一步放大存储和管理开销
5. **首次物化延迟**：冷启动的初次物化（捕获 + 序列化）仍需完整的 CUDA 图构建时间，热启动优势在首次部署时无法体现

## 💡 启发与我的想法

### 可借鉴之处

1. **"物化"思想的普适性**：将"每次重复计算的确定性结果"离线预计算并持久化，这一模式在系统优化中极具价值。类似地，KV Cache 前缀共享（Prefix Caching）也是对"固定 prompt 的 KV Cache 可复用"这一事实的物化利用
2. **地址非确定性的工程解法**：Medusa 的语义标签（Semantic Map）+ 触发内核双机制，提供了一个实用的工程模式，可推广到其他需要序列化/恢复 GPU 计算图的场景
3. **两阶段协作设计**：离线计算 + 在线轻量恢复的模式，是性能优化中的经典分层设计，值得在其他高冷启动开销场景中借鉴

### 改进空间

1. **渐进式物化**：对于动态形状场景，可以设计"渐进式物化"策略——首次遇到某形状时触发物化，后续相同形状直接复用，形成自适应的形状-物化映射缓存池
2. **物化快照压缩**：CUDA 图节点参数中大量是结构化数据，可以应用增量编码或领域特定压缩，减少持久化存储开销
3. **与 KV Cache 前缀缓存结合**：在物化 KV Cache 初始状态的基础上，进一步支持常见系统 prompt 的 KV Cache 预填充物化，使冷启动实例在服务首个请求时就能跳过 prefill 阶段

### 与已有笔记的关联思考

- **[[MemCopy]]（How to Copy Memory, SOSP'25）**：MemCopy 研究操作系统层面异步内存拷贝服务，Medusa 的模型权重并行加载与其在思路上高度相关——都在将 I/O 等待时间与计算时间重叠。Medusa 场景下若能利用 OS 级异步拷贝服务，理论上可进一步压缩权重加载时间
- **[[ZipServ]]**：ZipServ 关注 LLM 推理服务效率，与 Medusa 聚焦无服务器冷启动优化，二者在"减少首次 token 延迟"目标上高度契合，可以互为参考
- **[[MSched]]**：推理调度系统，与 Medusa 的无服务器实例调度策略存在协同空间——Medusa 提供快速冷启动能力，而 MSched 类系统负责决定何时/在何处触发冷启动
