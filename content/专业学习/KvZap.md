## 🧠 核心摘要 (TL;DR)

> KVzap简单来说就是训练了一个模型来根据每层的输出结果来评估这个token对本次上下文是否重要。这里没有直接依赖整个文本，而是通过每层的输出（已经attention过了）来隐式包含上下文数据，用了mlp来增强表达能力。 KVzap 采用了一种基于分数的全局阈值策略 ，设定一个固定的全局阈值.只有大于这个值的KV才会被保留。这种机制赋予了 KVzap 输入自适应性（Input Adaptivity）。实验数据显示，在固定的阈值下，不同提示词（Prompt）的有效压缩率波动幅度可达 20\% 。这说明 KVzap 能够像人类读者一样，遇到“干货”时读得慢一点（保留更多 Cache），遇到“水词”时读得快一点（剪枝更多）。尽管 KVzap 的预测相当准确，但在语言模型中，最近的上下文（Local Context）对于维持句法连贯性（如主谓一致、指代消解）至关重要，且这些 token 的长期价值往往尚未完全显现。并且对于decode，不能刚输出就直接丢弃，因为这样直观上就影响正确性。为了防止误删“新鲜”的 token，KVzap 引入了一个强制性的滑动窗口，大小固定为 128 个 token (11)。无论预测分数如何，最近生成的 128 个 token 永远会被保留在 Cache 中。这形成了一种混合存储结构:近期缓冲区： 稠密存储，保证句法正确性;长期记忆区： 稀疏存储，仅保留高价值信息，负责语义召回

## 🎯 1. 动机与痛点
在 Transformer 的自回归解码过程中，为了避免重复计算历史 token 的键（Key）和值（Value）向量，系统会将每一层的 KV 向量存储在显存中，形成 KV Cache。随着序列长度 的增加，KV Cache 的体积呈现 的线性增长。对于一个像 Llama-3-70B 这样的大模型，当上下文长度达到 128k 时，仅 KV Cache 就可能占据数百 GB 的显存，远远超过了单张顶级 GPU（如 NVIDIA H100 80GB）的容量 。  

### KV Cache 的“显存墙”问题

KV Cache 的膨胀直接导致了两个关键问题：
1.  **显存容量限制（Capacity Limit）：** 巨大的 KV Cache 挤占了原本用于存储模型权重和激活值的空间，迫使推理引擎不得不减小批处理大小（Batch Size）。这直接降低了 GPU 的计算利用率，增加了单位 token 的生成成本。
    
2.  **内存带宽瓶颈（Bandwidth Bottleneck）：** 在解码阶段，每生成一个新的 token，GPU 都需要从高带宽内存（HBM）中读取整个 KV Cache 到计算单元。随着 Cache 的增大，数据搬运的时间远超计算时间，导致推理过程从“计算密集型”退化为“访存密集型”，严重拖慢了首字延迟（TTFT）和解码吞吐量 。  

### 现有解决方案的局限性

为了缓解这一问题，学术界和工业界提出了多种方案：

-   **架构优化：** 如多查询注意力（MQA）和分组查询注意力（GQA），通过减少 KV 头数来压缩 Cache 。虽然有效，但它们只是减缓了增长斜率，并未改变线性增长的本质。  
    
-   **启发式剪枝：** 如 H2O (Heavy Hitter Oracle) 和 SnapKV，利用注意力分数的历史统计特征来剔除“不重要”的 token 。然而，这些方法往往基于“过去的重要性预示未来”的假设，容易在长距离依赖任务中丢失关键信息（如位于文档开头的人名或定义）。  
    

在此背景下，KVzap 应运而生。它摒弃了基于历史统计的启发式规则，转而采用一种“学习型”的方法，通过训练一个轻量级的代理模型来预测每个 token 在未来的潜在价值，从而实现既高效又“忠实”的剪枝 。  

## ⚙️ 2. 理论基石：从 Oracle 评分到 KVzip+
要深入理解 KVzap 的创新，必须首先剖析其背后的理论基石——KVzip 及其改进版 KVzip+。KVzap 的核心思想并非凭空创造一种新的重要性定义，而是通过蒸馏（Distillation）的方式，去逼近一个计算昂贵但极其精准的“Oracle”（神谕）评分器。

### 2.1 KVzip：基于重构的重要性定义
KVzip是 KVzap 的前身，它提出了一种基于“上下文重构”的重要性评估方法。传统的剪枝方法往往关注 token 在生成过程中的即时注意力权重，而 KVzip 认为，一个 KV 对的重要性取决于它对于**重构原始上下文**的贡献度 。  

为了量化这一点，KVzip 设计了一个“复制-粘贴”（Copy-and-Paste）的代理任务。给定一段上下文$C$ ，系统构造一个提示词：

$$\text{Prompt} = C \oplus \text{"user: Repeat context. assistant:"}$$

在这个任务中，模型被要求逐字复述之前的上下文。KVzip 定义第 个 $i$  token 的重要性分数 $S_i$ 为：在复述过程中，==所有后续生成的 token 对位置 $i$  的最大注意力权重==。 

$$s_i = \max_{j \in \text{Generation}} a_{ji}$$

==这个定义的直观含义是：如果一个 token 在复述整个上下文时从未被强烈关注过，那么它对于维持上下文的语义完整性可能是冗余的。KVzip 证明了这种方法可以在极高的压缩率下（如 400 倍）保持核心语义不丢失== 。  

然而，KVzip 存在致命的工程缺陷：它是一个**离线**且**非因果**的方法。要计算分数，必须先让模型“看到未来”（即完成复述任务），这需要将上下文长度翻倍并进行完整的预填充（Prefill），计算成本极高，且无法在流式解码（Decoding）阶段实时应用 。  

### 2.2 KVzip+：引入残差流贡献的精细化评分

KVzap 的研究团队在 KVzip 的基础上进一步深入，发现了原始注意力权重$a_{ji}$的局限性。注意力权重仅代表了概率分布，却忽略了向量本身的模长（Magnitude）。在 Transformer 中，最终影响模型输出的是残差流（Residual Stream）的更新量。一个 token 即使获得了较高的注意力权重，如果其 Value 向量的模长很小，或者相对于当前的隐藏状态 $h_j$ 微不足道，那么它对推理结果的实际影响依然有限。

因此，研究者提出了 **KVzip+**。这是一种增强版的 Oracle 评分机制，它引入了 Value 向量和隐藏状态的模长归一化项 ：  
$$s^{+}_{i} \propto a_{ji} \cdot \frac{||v_i||}{||h_j||}$$


-   $||v_i||$：代表第$i$ 个 token 的 Value 向量的强度。
    
-   $||h_j||$：代表查询位置 的隐藏状态的强度。
    

通过这种修正，KVzip+ 分数不仅反映了“关注度”，更反映了“实际贡献度”。实验表明，基于 KVzip+ 的评分与模型下游任务精度的相关性显著高于原始的 KVzip，为后续的监督学习提供了更高质量的标签（Ground Truth）。  

### 2.3 KVzap 的核心假设：从计算到预测

KVzap 的核心突破在于它将 KVzip+ 这个昂贵的“事后诸葛亮”转化为通过当前信息进行“事前预测”。

**假设：** 一个 token 在未来的重要性（即其 KVzip+ 分数）与其当前的隐藏状态 存在强映射关系。

基于此假设，KVzap 训练了一个轻量级的代理模型$f_{\theta}$ ，直接从 token 生成时的隐藏状态预测其对数重要性分数 ：  
$$\log(s^{+}_{i}) \approx f_{\theta}(h_i)$$

这一转变将复杂度从  $O(T^2)$（Oracle 方法需要全上下文交互）降低到了$O(1)$ （仅依赖当前 token），使得在线、低延迟的剪枝成为可能。


## 3. KVzap 架构解析与算法设计
KVzap 并非一个独立的模型，而是一个嵌入到 Transformer 每一层中的插件模块。其设计哲学是在保持极低计算开销（Overhead）的同时，最大程度地拟合 KVzip+ 的评分分布。

### 3.1 代理模型架构：线性 vs. MLP

为了在精度与速度之间寻找最佳平衡点，研究团队探索了两种代理模型架构 ：  

1.  **KVzap-Linear（线性版）：**
    
    -   **结构：** 仅包含一个线性投影层$W \in \mathbb{R}^{D_{model} \times H}$ 。
        
    -   **原理：** 假设重要性特征在隐藏空间中是线性可分的。
        
    -   **开销：** 极低，仅增加约 **0.02%** 的层级 FLOPs。
        
    -   **适用场景：** 对延迟极其敏感的超高吞吐场景。
        
2.  **KVzap-MLP（多层感知机版）：**
    
    -   **结构：** 一个包含两层的 MLP，激活函数采用 GELU。中间隐藏层宽度设置为模型隐藏维度的$1/8$（$D_{hidden}/8$）。
        
    -   **原理：** 利用非线性变换捕捉更复杂的语义特征（如句法结构、实体指代等），从而更准确地预测重要性。
        
    -   **开销：** 依然很低，增加约 **1.1%** 的层级 FLOPs。
        
    -   **表现：** 实验证明，MLP 版本在与 Oracle 分数的拟合度（$R^2$ 相关系数）上始终优于线性版，且在下游任务中表现更稳健 。  
        
==说白了Oracle是有先验的天眼数据，kvzip训出来如果跟Oracle拟合的好，就说明效果好==

### 3.2 自适应阈值剪枝机制（Adaptive Thresholding）

传统的剪枝方法（如 H2O）通常采用 Top-K 策略，即每一步强制保留固定数量（如 1024 个）的 token。这种方法的缺陷在于它忽略了不同输入文本的信息密度差异。一段充满技术术语的论文摘要显然比一段充满寒暄的日常对话包含更多关键信息，如果强制使用相同的预算（Budget），前者会丢失关键细节，后者则保留了冗余信息。

KVzap 采用了一种**基于分数的全局阈值策略** ：  

-   设定一个固定的全局阈值 $\tau$ 。
    
-   对于每一个 token $i$ ，计算预测分数$S_{pred} = f_{\theta}(h_i)$ 。
    
-   若$S_{pred} < \tau$ ，则该 token 的 KV 对被立即从缓存中剔除（Eviction）。
    
-   若 $S_{pred} \ge \tau$ ，则保留。
    

这种机制赋予了 KVzap **输入自适应性（Input Adaptivity）**。实验数据显示，在固定的阈值下，不同提示词（Prompt）的有效压缩率波动幅度可达 **20%** 。这说明 KVzap 能够像人类读者一样，遇到“干货”时读得慢一点（保留更多 Cache），遇到“水词”时读得快一点（剪枝更多）。  

### 3.3 滑动窗口保护机制（Sliding Window Safety Net）

尽管 KVzap 的预测相当准确，但在语言模型中，最近的上下文（Local Context）对于维持句法连贯性（如主谓一致、指代消解）至关重要，且这些 token 的长期价值往往尚未完全显现。

为了防止误删“新鲜”的 token，KVzap 引入了一个强制性的**滑动窗口**，大小固定为 **128 个 token** 。无论预测分数如何，最近生成的 128 个 token 永远会被保留在 Cache 中。这形成了一种混合存储结构：  

-   **近期缓冲区：** 稠密存储，保证句法正确性。
    
-   **长期记忆区：** 稀疏存储，仅保留高价值信息，负责语义召回。
    

## 4. 训练方法论与数据科学

KVzap 的成功高度依赖于代理模型的训练质量。如何让一个小小的 MLP 学会复杂的注意力分布规律？这涉及到精细的数据工程和监督学习设计。

### 4.1 数据集构建：Nemotron 的精选样本

为了获得通用性强的重要性特征，研究团队没有使用指令微调（SFT）数据，而是选择了 **Nemotron-Pretraining-Dataset-sample** 作为训练源 。  

-   **数据筛选：** 从海量预训练语料中筛选出长度在 **750 至 1,250 token** 之间的文本。这个长度区间既足够长，能够包含长距离依赖，又不会导致 Oracle 标签的计算成本过高。
    
-   **采样策略：** 为了保证数据多样性并防止过拟合，对每个子集采样 500 个提示词，并在每个提示词中采样 500 个 token 位置。
    
-   **规模：** 最终构建了包含约 **120 万个训练对**（Hidden State KVzip+ Score）的数据集，以及 2.3 万个验证对 。  
    

**洞察：** 使用预训练数据而非 SFT 数据是一个关键决策。预训练数据包含了自然语言的底层统计规律，这使得 KVzap 能够学习到通用的语言学重要性（如“名词通常比介词重要”），而非过拟合于特定对话模板（如“User/Assistant”标签）。

### 4.2 训练目标与回归分析

训练过程本质上是一个回归问题。目标函数是最小化预测分数与 Oracle 分数（对数域）之间的均方误差（MSE）。

在评估指标上，研究者重点关注**皮尔逊相关系数的平方（Squared Pearson Correlation, ）**。

-   **结果：** 训练后的 KVzap 代理模型在验证集上取得了 **0.63 至 0.77** 的 分数 。  
    
-   **解读：** 虽然没有达到 1.0 的完美拟合，但 0.7 左右的相关性足以保证 token 的**相对排序**是正确的。在剪枝任务中，只要能准确区分“最重要的 10%”和“最不重要的 50%”，具体的绝对分数值并不影响最终的保留决策。
    



## 📊 5. 实验与性能评价 
为了验证 KVzap 的有效性，研究团队在多个主流模型（Qwen3-8B, Llama-3.1-8B-Instruct, Qwen3-32B）及高难度基准测试（RULER, LongBench, AIME25）上进行了广泛的评估 。  

### 5.1 RULER 基准：大海捞针的考验

RULER 是一个专为长上下文设计的合成基准，包含了经典的“大海捞针”（Needle-in-a-Haystack）测试及多跳推理任务。

-   **表现：** KVzap 在 Qwen3-8B 上实现了超过 **70%** 的缓存剪除（即 3.3倍压缩），同时精度损失几乎为零 。  
    
-   **分析：** 在“大海捞针”任务中，关键信息（Needle）通常只是一个短语或数字，其余 99% 都是干扰文本。KVzap 的高分表明它能够精准地识别并锁定这些稀疏的关键节点，将其“钉”在缓存中，而将大量无关的干扰信息剔除。
    

### 5.2 LongBench：真实文档的复杂性

LongBench 包含小说摘要、代码补全、长文档问答等真实场景任务。与 RULER 相比，真实文本的信息密度更高，冗余度更低。

-   **结果：** KVzap 在此处实现了 **2倍 至 3倍** 的压缩率 。相比 RULER 的高压缩率有所下降，但这恰恰体现了 KVzap 的自适应性——面对高密度的真实文档，它自动降低了剪枝力度以保护信息。  
    
-   **对比：** 在相同压缩率下，KVzap 的 Rouge-L 和 F1 分数显著优于 H2O 和 SnapKV，证明了其在处理复杂语义依赖时的优越性。
    

### 5.3 AIME25：数学推理的脆弱性

AIME25 测试的是高难度的数学竞赛题目。这是一个对上下文极其敏感的领域，任何一个数字或运算符的丢失都可能导致推理链条（Chain-of-Thought）的断裂。

-   **惊人发现：** 在约 2倍 压缩率下，KVzap-MLP 甚至略微**提升**了 Pass@4 的准确率 。  
    
-   **解释：** 这种反直觉的提升可能归因于“去噪效应”。在数学推理中，过长的无关上下文可能会干扰注意力机制的聚焦。KVzap 通过剔除无关信息，相当于为模型做了一次“注意力聚焦”，使其更专注于当前的推理步骤。
    
-   **崩溃点：** 当压缩率极其激进（如 >90%）时，性能如预期般崩塌 。这划定了物理极限：即使是最冗余的文本，也存在最小信息熵的下界。

## 6. 其他方案对比 
在 KVpress 排行榜上，KVzap 与众多现有的剪枝方法进行了同台竞技。我们将 KVzap 与几类主流方法进行深度对比。

### 6.1 KVzap vs. H2O (Heavy Hitter Oracle)

H2O 是启发式剪枝的代表，它基于“累积注意力分数”进行保留。

-   **H2O 的短板：** H2O 存在“流失”风险。如果一个关键 token 出现在文章开头，但中间有几千个 token 没有关注它，它的累积权重就会下降，最终被 H2O 剔除。当文章结尾突然需要回顾这个 token 时，它已经不在缓存中了。
    
-   **KVzap 的优势：** KVzap 是基于**内容**（Hidden State）预测重要性，而非基于**历史热度**。只要 token 本身的语义特征表明它是一个“值得记忆的概念”（如人名、定义），KVzap 就会在一开始给它高分并长期保留，不受中间注意力的干扰。
    

### 6.2 KVzap vs. SnapKV

SnapKV 利用聚类算法识别注意力模式。

-   **对比：** SnapKV 的操作粒度较粗（通常是块级别或簇级别）。KVzap 实现了 token 级别的精细化管理。在 LongBench 等需要精细阅读的任务中，KVzap 的颗粒度优势使其能保留更多细节。
    

### 6.3 KVzap vs. 架构压缩 (GQA/MLA)

-   **互补性：** GQA（分组查询注意力）和 MLA（多头潜在注意力，DeepSeek-V2 采用）是在\*\*头（Head）**和**维度（Dimension）**轴上进行压缩。KVzap 是在**时间（Time/Sequence）\*\*轴上进行压缩。
    
-   **未来形态：** 最极致的推理引擎必然是二者的结合。例如，一个使用 MLA 架构的模型，配合 KVzap 进行时间轴剪枝，可以实现数量级的显存节省。
    

## 7. 硬件实现与工程挑战
虽然 KVzap 在算法层面表现优异，但在实际的 GPU 推理引擎（如 vLLM, TensorRT-LLM）中落地，仍面临具体的工程挑战 。  

### 7.1 稀疏性与不规则内存访问

KVzap 的自适应特性意味着：

1.  **不同 Head 的 Cache 长度不同：** 某些 Head 可能关注语法，保留较多 token；另一些 Head 关注特定实体，保留较少。
    
2.  **不同 Batch 的 Cache 长度不同：** 不同输入 Prompt 的保留率不同。
    

这导致了 KV Cache 在物理显存中呈现出高度的**稀疏性（Sparsity）**和**参差不齐（Raggedness）**。

-   **挑战：** 现代 GPU 的 SIMT（单指令多线程）架构最擅长处理规则的稠密矩阵运算。参差不齐的张量会导致线程束分歧（Warp Divergence）和非合并的内存访问（Uncoalesced Memory Access），严重降低 FlashAttention 等内核的效率。
    
-   **解决方案：** 需要定制化的 CUDA 内核，类似于 PagedAttention 的改进版，能够高效地管理非均匀的块（Block），并支持基于索引表（Indirection Table）的快速 gather/scatter 操作。
    

### 7.2 计算开销与延迟权衡

-   **增量开销：** 引入 MLP 代理模型确实增加了计算量。对于 8B 模型，每层增加 1.1% 的 FLOPs 看似微小，但在极高吞吐场景下（如每秒生成数千 token），这也是不可忽视的成本。
    
-   **净收益：** 然而，考虑到 Attention 操作本身是 的（在线性 Attention 优化前），且受到显存带宽限制。通过剪枝将 减小 3-4 倍，所带来的带宽节省和 Attention 计算减少，远远超过了 MLP 带来的微小开销。在长上下文（>10k tokens）场景下，KVzap 带来的端到端延迟降低是显著的。
    

## 💡 启发与我的想法 

### 忠实性（Faithfulness）的哲学

KVzap 报告中反复提及“忠实性”一词。这代表了压缩理念的转变：

-   **旧范式：** “只要输出看起来通顺，怎么剪都行。”（基于 Perplexity 的评估）
    
-   **新范式（KVzap）：** “模型必须像拥有全缓存一样思考。”（基于 Attention 行为的评估）
    

KVzap 通过回归 KVzip+ 分数，实际上是在模仿全量模型的注意力分布。这对于金融、法律、医疗等高风险领域至关重要。在这些领域，仅仅“看起来通顺”是不够的，必须保证推理逻辑的严谨性，不能因为剪枝而产生幻觉（Hallucination）。

### 局限性与未来工作

尽管表现出色，KVzap 并非完美 ：  

1.  **预训练分布依赖：** 代理模型是在 Nemotron 数据上训练的。如果用户输入的是极为罕见的异构数据（如特殊的二进制代码、古文），代理模型的预测可能会失效。未来的工作可能涉及 KVzap 模块的**领域自适应微调（Domain Adaptation）**。
    
2.  **对超长序列的验证：** 目前实验主要集中在 100k 级别。对于 1M 甚至 10M 级别的超长序列，简单的 MLP 是否还能有效捕捉全局重要性，仍需进一步验证。==一方面是单层的MLP是否足够学会重要性判断，另一方面是KVzap受限于隐藏状态（Hidden State）的信息容量，在极端的超长上下文中，这必然会成为一个瓶颈并带来信息损失== 不过代理模型不需要从 $h_i$ 中还原所有复杂的上下文交互细节。它只需要从这个高维向量中提取一个非常简单的标量信号：“当前这个词包含的信息密度大不大？”。对于判断一个词是否是实体、专有名词或关键逻辑节点，固定维度的 $h_i$ 所包含的信息量通常已经足够了。
    
3.  **工程集成：** 尚未直接集成入 vLLM 等主流框架，这限制了其即插即用的普及度。 

4.  **注意力偏移问题：**   相关性可能是在后期才发生的，想象一个多轮对话场景，用户给出的前缀数据在最开始的几个问题中确实毫无作用，但是多轮对话之后，突然要求回头看某个词，kvzap却已经丢弃了，这是不可逆的。这也是KVzap以及绝大多数“前向预测型” KV Cache 剪枝方法的核心软肋。==但它在评估一个 token 时，看重的不是它对前几个问题有没有用，而是**这个词本身包含的信息密度高不高，对于维持整段话的语义完备性重不重要**==因为 KVzap 的代理模型是在大规模预训练语料上学习的，它学到了通用的语言学规律。即便前缀数据在最开始的几轮对话中没被提及，但只要这些数据包含实体、专有名词、时间、数值等核心概念，KVzap 在生成它们的瞬间就会赋予高分并将其永久锁定在缓存中。

### 发散讨论
**前向剪枝确实有自身缺陷**：如果出现极端情况——比如用户在多轮对话后，突然要求模型回顾一个原本毫无信息量的过渡词（例如：“你最开始回复我的第一句话的第 5 个字是什么？”），KVzap 绝对会被击穿，因为它早就把那个看似无用的词当作噪音不可逆地丢弃了。为了解决这种长尾问题，业界只能探索诸如动态从 CPU 内存取回数据（SpeCache）等更复杂的系统级方案，但这往往又会牺牲 KVzap 所追求的极致低延迟。

**基于mlp的重要性预测**：KVzap 本质上是用理论上必然存在的信息损失，去换取极致的 $O(1)$ 打分速度和 2-4 倍的显存节省。在当前 100K-200K 的上下文窗口内，这种折中在工程上是极其划算的；但如果未来模型走向无限上下文，这种依赖单一隐藏层向量进行打分的机制，确实可能需要被重新审视。

**查询感知（Query-Aware）还是查询无关（Query-Agnostic）**：KVzap属于一种查询无关的方法，比如对于##RULER##类题目，一开始给了几万字维基百科的无关内容，中间插入了一句 **“特工的保险箱密码是 83920”** 。KVzap遇到“的”、“是”、“而且”、“大家知道”这些语法连接词或低信息熵词汇，KVzap 会给极低的分数，直接丢弃。遇到“爱因斯坦”、“1905年”、“相对论”、“E=mc²”这些专有名词、数字或实体，KVzap 会认为这是高密度信息，给它们打高分，并将其保留在 KV Cache 中。当遇到“针”（Needle）时： 假设在几万字的维基百科中，突然突兀地插了一句“特工的保险箱密码是 83920”。因为这句话极具特异性，且包含高度浓缩的实体（密码、数字），KVzap 的模型会瞬间识别出这是一个高价值语义节点，从而赋予极高的分数并永久锁定。==核心还是原始信息中有大量冗余信息，才能压缩，否则全部都是“密码是多少”这里关键信息的话，就没得压缩了，只有带着查询信息的，才能精准过滤==
