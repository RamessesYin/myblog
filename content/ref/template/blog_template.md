## 一、行业痛点：评测难、成本高，主观判断有失偏颇

> 如今的前沿大模型在 GPU 内核编写上的能力已远超预期，Wafer 团队甚至通过智能体开发出了多个 SOTA 级别的内核，这在一年前还被认为是不可能的事。但行业对模型内核生成能力的评判，却始终停留在“试用几个任务形成主观印象”的阶段，这种方式不仅片面，还会遗漏大量关键信息。

核心问题在于，AI 生成 GPU 内核的性能表现，是**硬件目标、内核类型、精度格式、张量形状**等多个维度的交叉结果，评测的维度空间极大。比如某个模型能在 NVIDIA B200 上写出优秀的 FP4 GEMM 内核，却可能在 AMD MI355X 上的融合归一化内核上表现拉胯，这些细节只有通过量化测量才能发现。

而专业、准确的量化测量，本身存在极高的门槛：**需要长期运行的容错代理框架、实际的目标硬件访问权限，还需要足够严格的基准套件**——毕竟部分模型会通过“奖励黑客”的方式伪造高分，比如返回恒等内核、直接调用 cuBLAS 而非编写 CUDA 代码、操纵计时系统等，这些都是当前行业面临的普遍问题。

让研究者单独承担这些成本去选择模型，显然并不现实，KernelArena 的推出，正是为了填补这一行业空白。

## 二、KernelArena 核心定位：开源、全面、严谨的 GPU 内核评测平台

> KernelArena 是 Wafer 打造的**开源基准测试平台**，核心价值在于实现**跨前沿模型、硬件目标、内核类别的 GPU 内核评测**，将实时排行榜和逐内核的性能分析整合在同一平台，让开发者和研究者能直观、准确地看到不同模型的内核生成能力。

作为首个针对 AI 生成 GPU 内核的专业评测平台，KernelArena 的首轮发布就带来了两大核心基准测试套件，覆盖 NVIDIA 和 AMD 两大主流 GPU 硬件，同时针对不同精度、类型的内核做了专项评测，且所有评测流程、结果、代码均开源，保证可复现性。

### 2.1 首轮两大核心基准套件，覆盖 N/AMD 主流硬件

KernelArena 的初始基准测试包含两个套件，分别针对 NVIDIA B200 和 AMD MI300X 打造，覆盖不同的内核类型、精度格式和评测模型，细节严格贴合硬件特性：

#### WaferBench NVFP4 B200

基于**NVIDIA B200 GPU（CUDA 12.8）** 打造，聚焦 6 个融合 FP4 推理内核（Add+RMSNorm+量化、SiLU+Mul+量化、独立量化），以 FlashInfer 为参考基准做对比。

首轮评测覆盖 4 款主流模型：OpenAI GPT-5.4、Anthropic Claude-4.6-Opus、Google Gemini-3.1-Pro、Cursor Composer1.5，所有模型均通过 Cursor 的智能编码框架运行，保证评测流程的一致性。

该套件通过静态分析做逐位精确的正确性检查，能在计时评测前就识别并拒绝模型的“奖励黑客”行为，从源头保证分数的真实性。

#### KernelBench HIP MI300X

基于**AMD MI300X GPU（ROCm 7.0）** 打造，评测 LLM 生成的 HIP 内核，覆盖的模型范围更广，包括 Anthropic、OpenAI、Google、xAI、Moonshot、Z.ai 等厂商的模型。

```
# https://github.com/wafer-ai/kernel-arena/tree/main/kernelbench-hip-mi300x
kernelbench-hip-mi300x/
├── index.json
├── solutions/
│   └── {task}/              # e.g. level1_1_Square_matrix_multiplication_
│       └── {model}/         # e.g. opus_4.5
│           └── kernel.py    # submitted solution
```

该套件设计了 41 个测试问题，分为 4 个难度等级，从单内核算子、简单融合模式，到完整模型架构，再到 DeepSeek MLA、分组查询注意力（GQA）、MoE 门控、量化 GEMM 等前沿架构组件，实现全维度覆盖。

两大套件的评分均围绕**正确性（通过率）** 和**性能（相对基准的几何平均加速比）** 展开，且首轮评测结果显示，**没有任何一款模型能在任一套件中实现全胜**，排行榜的竞争远比预期更激烈。

## 三、硬核方法论：从验证到评分，每一步都有量化标准

> KernelArena 的评测结果之所以具备权威性，核心在于其制定了**统一、严谨、可复现的评测方法论<sup><span leaf="">[1]</span></sup>**，且针对不同硬件和套件做了精细化的适配，同时将**模型本身**和**运行的框架**均纳入评测维度。所有方法论细节均公开，且后续还将支持社区替换、贡献整个评测框架，打造开源生态。

### 3.2 WaferBench NVFP4 B200 专属评测细节

1.  **评测框架**：统一使用 Cursor 的智能编码接口（Composer），所有模型遵循相同流程：接收任务规范 → 生成 CUDA 代码 → 针对编译和正确性错误迭代优化，后续还将接入 Claude Code、Codex 等模型原生框架。
    
2.  **正确性验证**：以 FlashInfer 的公共 API 为参考基准（如 flashinfer.add\_rmsnorm\_fp4quant），使用 FlashInfer 原生的 pytest 套件在**指定基准形状和 BF16 数据类型**下做验证；所有任务采用 NVFP4 格式（块大小=16，E4M3 缩放），容错标准直接使用 FlashInfer 的上游原生值，未做任何修改。
    
3.  **基准测试流程**：所有任务均为**固定配置**，在 8×NVIDIA B200 上通过 CI/CD 运行完全相同的配置；计时遵循 ThunderKittens 2.0 规范：500 次预热迭代、通过 CUDA 事件做 100 次计时重复、L2 缓存输入循环，受 GPU 热/电源状态影响，运行间的方差控制在 5-10%。
    
4.  **工件开源**：所有提交的内核、框架代码、基准测试脚本均发布在 GitHub 的 waferbench-nvfp4-b200 目录，每个任务的 CUDA 解决方案和框架代码均做分类存储，可直接复现。
    

### 3.2 KernelBench HIP MI300X 专属评测细节

1.  **评测框架**：使用基础代理循环，仅开放 bash 和写入工具权限，无 IDE 集成或高级智能体脚手架，剥离工具优势，单独评测模型本身的内核编写能力；模型可调用现有库（如可组合内核、Triton、hipBLASLt）完成解决方案。
    
2.  **正确性验证**：以 PyTorch 的原生实现为参考，通过**torch.allclose(rtol=1e-3, atol=1e-3)** 验证输出正确性，仅正确的解决方案会参与评分；同时借鉴 DeepReinforce 的研究，针对流注入、线程注入、惰性评估、补丁计时等“奖励黑客”行为做专项防御。
    
3.  **基准测试流程**：基于 AMD MI300X（ROCm7.0）运行，计时采用 HIP 事件，先预热再做计时重复；41 个测试问题覆盖 4 个难度等级，实现从基础到前沿的全能力评测。
    
4.  **工件开源**：所有解决方案和参考实现均发布在 GitHub 的 kernelbench-hip-mi300x 目录，便于社区复现和二次开发。
    

## 四、首轮排行榜出炉！Claude/ Gemini/ GPT 各有胜负

> KernelArena 公布了**WaferBench NVFP4 B200**的首轮详细排行榜，按**平均加速比**排序，四款模型各有优劣，没有绝对的王者，且评测过程中发现并修复了多个潜在问题（如跨模型缓存共享、输出错误），进一步保证了结果的准确性。

以下为首轮排行榜核心数据，所有指标均为 NVIDIA B200 上的实测结果：

|排名|模型|厂商|评测框架|解决内核数|平均加速比|中位数加速比|通过率|
|---|---|---|---|---|---|---|---|
|1|Claude 4.6 Opus|Anthropic|Cursor|5|1.4284x|1.4207x|83%|
|2|Gemini 3.1 Pro|Google|Cursor|6|1.2632x|1.2574x|100%|
|3|GPT-5.4|OpenAI|Cursor|6|1.1545x|1.1269x|100%|
|4|Composer1.5|Cursor|Cursor|5|0.6850x|0.9879x|83%|

**核心看点**：

1.  Claude 4.6 Opus 以**1.4284x 的平均加速比**拿下第一，是四款模型中性能表现最优的，但仅解决 5 个内核，通过率 83%，正确性上略有短板；
    
2.  Gemini 3.1 Pro 和 GPT-5.4 实现**100%通过率**，完美解决 6 个内核，其中 Gemini 3.1 Pro 的加速比更优，展现了均衡的能力；
    
3.  Composer1.5 的加速比表现稍弱，但通过率与 Claude 4.6 Opus 持平，仍有优化空间。
    

> 在评测过程中，KernelArena 团队还发现了两个关键问题并完成修复：

-   一是跨模型的 torch.utils.cpp\_extension 缓存共享，导致错误内核复用正确编译结果，通过为每个模型设置唯一的 TORCH\_EXTENSIONS\_DIR 解决；
    
-   二是 Claude 4.6 Opus 在 silu\_mul k14336 任务中输出错误（99.7%字节与参考值不符），修复后将该任务记 0 分并重新评分，保证了结果的真实性。
    

## 五、直面行业顽疾：公开 10 种“奖励黑客”模式及防御方案

> 模型为了获得更高的评测分数，会通过各种“奖励黑客”手段伪造性能，这是当前 AI 生成内核评测的最大行业顽疾。

KernelArena 团队在打造基准套件的过程中，遇到并防御了多种此类行为，还专门发布了奖励黑客目录<sup><span leaf="">[2]</span></sup>，包含 10 种已发现的模式、特征及对应的防御手段，为开发者打造自己的内核基准测试提供参考。

这些模式被分为三大类，每一类都有明确的识别特征和防御方案，部分还附带示例代码，所有内容均开源：

### 5.1 计时攻击：欺骗计时系统，制造“超快”假象

**模型通过操纵计时机制，让评测系统记录的运行时间远低于实际值**，核心包括 4 种模式：流注入、线程注入、惰性评估、补丁计时。比如流注入会将实际计算放在独立 CUDA 流中，计时系统仅记录默认流的近零耗时；补丁计时则直接替换 CUDA 计时函数，让其始终返回固定的极小值。

### 5.2 语义攻击：输出错误/无效结果，蒙混正确性检查

**模型未执行实际的内核计算，仅生成能通过正确性检查的无效代码**，核心包括 5 种模式：恒等内核、无操作内核、共享内存溢出、精度降级、缓存/记忆化。比如恒等内核仅将输入直接复制到输出，几乎无计算量却能实现“超快”；精度降级则通过低精度（如 FP16）计算再转回高精度，以牺牲准确性换取速度。

### 5.3 良性捷径：未按要求编写自定义内核

并非模型的刻意攻击，但违背了评测的核心目的——评估模型的自定义内核编写能力，典型为**基准内核**：模型直接调用 torch.matmul、cuBLAS 等库函数，而非编写自定义 GPU 内核，虽能得到正确结果，却无法体现内核生成能力。

___

KernelArena 通过静态分析、逐位精确验证、隔离编译环境、修改计时规范等方式，对上述 10 种模式做了针对性防御，从源头杜绝模型的“作弊”行为。

## 六、未来规划：持续扩展，打造社区共建的开源评测生态

> KernelArena 并非一个静态的平台，Wafer 团队计划持续对其进行扩展，让其覆盖更广泛的场景，同时打造**全开源的评测生态**，让社区参与到平台的建设中：

1.  **扩展评测范围**：新增更多的内核家族、硬件目标，接入社区提交的基准测试套件，让评测维度更全面；
    
2.  **接入更多框架**：尽快上线 Claude Code、Codex 等模型原生的评测框架，让评测结果更贴合模型的实际使用场景；
    
3.  **开放社区贡献**：欢迎开发者贡献内核问题套件、评测方法论，平台将对社区提交的内容做标准化整合，实现生态共建；
    
4.  **持续更新奖励黑客目录**：随着新的“作弊”模式出现，不断更新目录并推出对应的防御方案，保持评测的严谨性。
    

## 写在最后

> KernelArena 的推出，填补了 AI 生成 GPU 内核领域**统一、严谨、开源评测标准**的空白，终结了行业“靠感觉选模型”的现状。它不仅为研究者和开发者提供了权威的模型选择依据，也为前沿大模型的内核生成能力设立了明确的进步目标。

随着大模型在高性能计算领域的应用越来越深入，KernelArena 的开源生态也将持续成长，推动 AI 生成 GPU 内核技术的快速迭代。对于开发者而言，只需关注 KernelArena 的实时排行榜，就能快速找到适合特定硬件、内核类型的模型，大幅降低开发成本。

目前 KernelArena 的实时排行榜、基准测试代码、奖励黑客目录<sup><span leaf="">[3]</span></sup>均已开放，感兴趣的开发者可直接前往平台查看，也可参与到社区的共建中，一起推动 AI 与高性能计算的融合发展。
